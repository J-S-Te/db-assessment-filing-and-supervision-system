# U2 备案办理 · ② 抽取结果与表单回填 —— 全量承载方案

> 目标：把门户端《等级保护备案信息填写》的 **6 张表 + 1 份定级报告** 完整纳入用户端 ② 区，且不破坏"智能抽取 → 人工确认"的产品语义。
>
> 涉及文件：
> - 用户端：`原型/用户端/用户端index.html`（第 262–322 行 `#u2-t2`）
> - 门户端：`原型/用户端/客户与商机管理子系统-门户端.html`（第 710–1107 行，filing wizard 7 步）
> - 样式：`原型/用户端/user.css`

---

## 一、结论先行

**不要"把 7 步向导搬进用户端"，也不要"把 103 个字段平铺进 form-grid"。**

推荐形态：**覆盖率总览条 + 左章节目录 + 右分区工作台 + 底部固定确认条**，交互主轴从"逐步录入"改为**"异常驱动"**。

一句话理由：门户端是**人工录入场景**，用户必须按顺序填完 7 步，向导是合理的；用户端是**结果审阅场景**，70% 字段已由 AI 填好，用户的核心动作只有"过一遍 + 处理 33 项异常"。再用 7 步向导，等于让用户点 7 次"下一步"去看一堆本来就对的内容，是负收益。

## 二、现状差距量化

| 维度 | 用户端 ②（现状） | 门户端 备案信息（目标） |
|---|---|---|
| 承载内容 | 8 个扁平字段 | 6 张表 + 1 份定级报告 |
| 字段量 | 8 | **103 项**（按可独立回填的控件计） |
| 分组层级 | 无（单个 form-grid） | 3 层：表 → 小节（一/二/三…）→ 字段 |
| 特殊控件 | 无 | 单选组、多选组、级联省市县、有/无 + 附件名、技术场景开关、可增行子系统表、涂黑式等级矩阵表 |
| 长文本 | 无 | 定级报告 5 段叙述 + 2 张矩阵表 + 结论表 |

**结论：8 → 103，且含 7 类非文本框控件。这不是"加内容"，是"换容器"。**

补充发现（建议顺手修）：门户端表1 缺少《备案表》实际要求的 **单位名称** 字段（只有信用代码、地址），已在本方案表1 中补入。

### L1 覆盖率总览条（新增）

- 7 个 chip（6 表 + 定级报告），每个显示 `表名` + `已回填/总数`，绿底=无异常，灰底=有待处理。
- 点击 chip = 跳转到对应章节（`scrollIntoView` + 高亮 800ms）。
- 第 8 格是过滤器：**"仅看异常 33 项"**，切换后工作区只渲染 `status ≠ filled` 的字段。
- 右侧总览文案：`70 / 103 字段已回填 · 22 待确认 · 8 缺失 · 3 冲突`。

### L2 左章节目录 + 右工作区

- 左栏 200px，7 章竖排，每项 `状态圆点 + 章节名 + n/N`；`position: sticky` 跟随滚动。
- 右栏按**小节**分组渲染（沿用备案表原小节标题"一、单位基本信息""（一）业务信息安全保护等级"），每个小节头显示 `n 项 · x 项待确认`，并提供 **"本小节 N 项一键确认"**。
- 章节默认**只展开当前项**，其余折叠为一行标题（避免 103 字段长页）。折叠态仍显示 `n/N` 与异常数。

### L3 底部固定确认条

- 常驻显示 `已确认 X / 103` + 进度条。
- `提交备案` 在存在 缺失/冲突 时**禁用**，按钮文案直接说明原因：`提交备案 · 33 项未处理`。
- 保留 `保存草稿`、`回到问答引导`。

## 五、字段状态模型（本方案的核心增量）

现有 `src-tag` 只有 `hi / mid / low` 三态。需扩到 **5 态**，并补两个交互属性。

| 状态 | 视觉 | 触发条件 | 用户动作 |
|---|---|---|---|
| `filled` 已回填 | 绿 tag「高置信」 | 单一来源，置信度 ≥ 阈值 | 抽查即可，可一键确认 |
| `pending` 待确认 | 灰 tag「待确认」 | 置信度中 / 来源于正文推断 | 确认或改 |
| `missing` 缺失 | 红虚线框 + 「未抽取到，需补录」 | 材料里没有 | 手填 |
| `conflict` 冲突（新增） | 红底框 + 「冲突 · 另作 xx」+「去裁决」 | 两份材料口径不一致 | 二选一采信 |
| `manual` 手工录入 | 蓝 tag「人工」 | 用户改过 AI 值 | 保留修改留痕 |

每个字段额外挂两项元数据：

1. **来源溯源**：`{ file, page, snippet }[]`。悬停 `src-tag` 弹出气泡 → `HIS系统建设方案V3.2.docx · 第 3 页` / 原文片段；点「查看原文」定位。
2. **变更留痕**：`{ from, to, at }`。改过的字段显示小灰「已修改」，供机构初审追溯。

**这套状态必须在 103 个字段上一致可用，这是"抽取结果"区别于"普通表单"的唯一证据。**

## 六、搬迁清单（6 表 + 1 报告 → 7 章节 / 103 项）

### 表1 单位基本情况（30 项）

| 小节 | 项数 | 字段 |
|---|---|---|
| 一、单位基本信息 | 7 | 单位名称（门户端缺，需补）、备案表编号、统一社会信用代码、行政区划（省/市/县 **合并为 1 个级联控件**）、详细地址、邮政编码、行政区划代码 |
| 二、单位负责人 | 4 | 姓名、职务/职称、办公电话、电子邮件 |
| 三、网络安全责任部门 | 6 | 部门名称、联系人、职务、办公电话、移动电话、电子邮件 |
| 四、数据安全管理部门 | 6 | 同上 |
| 五、单位属性 | 3 | 隶属关系、单位类型、行业类别（均为枚举 select） |
| 六、定级对象数量 | 4 | 第二/三/四/五级定级对象数 |

> 省/市/县三级输入合并为级联控件是必要的：103 项里有 3 项纯地址碎片，拆开会让表1 首屏显得非常"机械"。

### 表2 定级对象情况（17 项）

- 基本信息 3：定级对象名称、定级对象编号、定级对象类型（7 选多，复选）
- 承载业务情况 2：业务类型、业务描述（textarea）
- 网络服务情况 2：服务范围、服务对象
- 网络平台 5：部署范围、网络性质、源站 IP 地址范围、域名、主要协议/端口
- 互联与运行 5：网络互联情况、投入运行时间、是否分系统、上级系统名称、上级系统所属单位

> 「定级对象类型」是 7 个复选项，占位宽，**必须单独占满一行**，不能进 `form-grid` 的两列。

### 表3 定级情况（11 项）

业务信息安全保护等级、系统服务安全保护等级、定级对象安全保护等级、定级时间、定级报告（有/无 + 附件名）、专家评审情况、上级行业主管部门（有/无）、名称、审核情况、填表人、填表日期。

> 「有/无 + 附件名」这种复合控件共出现 **7 次**（表3 一处 + 表5 六处），必须抽成一个组件 `fieldYN()`，否则代码会失控。

### 表4 新技术应用（19 项）

5 个技术场景，每个 = `是/否 开关` + 明细区（选"否"时明细自动折叠）：

| 场景 | 明细字段 |
|---|---|
| 云计算 | 责任主体类型、服务模式、部署模式、云平台名称/等级、平台备案编号、运维地点（6，含开关） |
| 移动互联 | 应用/小程序名称、无线通道情况、移动终端情况（3） |
| 物联网 | 感知层（多选）、网络传输层（多选）（3） |
| 工业控制 | 功能层次（多选）、系统组成（多选）（3） |
| 大数据 | 系统组成（多选）、出境情况、应用数量、平台名称/备案编号（5，含开关） |

> **这是最容易失控的一张表**。建议：5 个场景做成 5 个折叠卡（默认只展开被 AI 判定为"是"的场景），每个场景头显示 `是/否` 徽标 + 已填 n 项。这样首屏只有 2–3 张卡，而不是 19 个字段。

### 表5 提交材料（6 项）

网络拓扑结构及说明、网络安全组织架构及管理制度清单、网络安全建设或整改设计方案、网络安全专用产品清单及安全证书、安全服务清单、行业主管部门指导定级文件。每项 = `有/无` + 附件名。

> **注意语义差异**：这张表在用户端不是"抽取结果"，是"**材料齐备度自检**"。已上传的材料应自动判"有"并回填文件名（关联 ① 上传区的 4 个文件），未上传的判"无/缺失"。这一联动是本方案的一个亮点，也是降低"机构退回补正"概率的关键。

### 表6 数据摸底（12 项）

数据名称、拟定数据级别、数据类别、数据安全责任部门、数据安全负责人、个人信息涉及情况（4 选多）、数据总量、月增长量、数据来源（5 选多）、单位间数据流转（可增行）、与其他处理者交互情况、数据存储位置（5 选多）。

> 4 个多选组 + 1 个可增行输入。可增行输入（数据来源单位/流出单位）建议先渲染 1 行 + "＋添加"，不要预留 3 个空框。

### 定级报告（8 段）—— **不做成表单，做成文书**

| 段落 | 内容 |
|---|---|
| 一（一） | 责任主体（建设/运维/安全主管/定级责任单位） |
| 一（二） | 定级对象构成（物理环境/网络结构/边界/安全措施/新技术） |
| 一（三） | 承载业务（业务情况/系统规模/互联情况）+ **可增行子系统清单表** |
| 一（四） | 承载数据（类别/级别/处理环节/流转） |
| 一（五） | 安全责任（责任单位/责任人） |
| 二（一） | 业务信息安全保护等级：描述 + 受侵害客体 + 侵害程度 + 等级 + **表一 矩阵表（涂黑）** |
| 二（二） | 系统服务安全保护等级：同上 + **表二 矩阵表（涂黑）** |
| 二（三） | 安全保护等级确定：结论段 + 结论表 + 盖章位 |

**特殊处理：定级报告用"左表单 / 右 A4 预览"双栏，而不是普通分组表单。**
- 左：8 段结构化字段（叙述段用 textarea，字数统计显示）。
- 右：A4 纸张比例的实时预览（白底、宋体、1.5 倍行距），改左边右边立刻变。
- 矩阵表：右侧预览里的单元格**可直接点选涂黑**，点选结果反写左侧"受侵害客体 / 侵害程度 / 等级"三个 select —— 三个控件与矩阵表双向绑定，避免用户两边填出矛盾。
- 「导出定级报告」按钮放在本章节头（与 ① 定级自评结果的导出按钮共用同一个动作）。

## 七、前端数据模型（建议）

```js
const EXTRACT_SECTIONS = [
  { id:'t1', code:'表1', name:'单位基本情况',
    groups: [
      { name:'一、单位基本信息', fields:[
        { key:'orgName', label:'单位名称', type:'text', required:true,

    ]
  },

```

- `status ∈ filled | pending | missing | conflict | manual`

- 事件：`jumpToSection(id)`、`confirmSection(id)`、`resolveConflict(key, idx)`、`toggleOnlyAbnormal()`、`recalcProgress()`

**全部为纯前端 mock 数据，不引入后端依赖，符合原型定位。**

## 十四、P1 实施记录（2026-10-19 已落地）

**范围**：仍只改用户端，门户端原型未动。P1 在 P0 骨架上补的是"交互闭环"，不新增章节、不改信息架构。

### 1. 表5 ↔ ① 上传区真正双向联动（原为静态文案）

新增 `UPLOADS` 数据模型（4 个上载槽）与 `syncUploads()`，表5 的三个可用材料项挂 `up` 键绑定到上载槽：

| 表5 字段 | 绑定上载槽 | 初始状态 |
|---|---|---|
| 网络拓扑结构及说明 | `topo`（已上传） | 高置信「有」+ 文件名 |
| 网络安全组织架构及管理制度清单 | `policy`（未上传） | **缺失**（原为高置信「有」，属假数据） |
| 网络安全建设设计方案或整改设计方案 | `plan`（已上传） | 待确认（版本号需核） |

- 上传：① 区点「＋ 上传」→ 槽位由空变满 → 表5 自动判「有」并回填附件名 → 进度条 / 章节 chip / 底部条 / ① 提示行同步。
- 移除：点文件名右侧「×」→ 表5 对应项立即转「缺失」，提交按钮拦截数 +1。
- 缺失项在表5 内不再给"补录"（会造出假附件名），改为「去 ① 上传该材料」并滚动高亮目标槽位。
- 表5 每个联动字段带 `① 联动` 徽标，来源行显示 `① 上传区 · <槽位名>`，从视觉上区分"抽取"与"上传"两种来源。

> 该联动使初始统计由 `70/22/8/3` 变为 `69/22/9/3`（总数仍 103）。这不是回归，是原先"制度清单"被硬编码成已有附件的假数据被纠正。

### 2. 逐字段确认（补上 P0 只有批量确认的缺口）

- 每个 `待确认` 字段下方一个「✓ 确认此项无误」，单点即转「人工」并立即联动进度。
- 冲突项与缺失项点确认会被拦下并提示"先选采信口径 / 先补录"，不允许空确认。
- **冲突不可被"打字"静默消解**：P0 中在冲突字段里输入任意字符会把状态刷成「人工」从而绕过裁决；现在冲突项保持「冲突」，必须显式点采信口径。

### 3. 异常项逐项导航（"仅看异常"的闭环另一半）

- 仅看异常模式下，工作区底部出现 `← 上一异常 · 异常 3 / 31 · 下一异常 →`，可跨章节连贯推进。
- 确认 / 采信 / 补录后自动落到下一项并高亮 1.4s，不需要手动回目录。
- 处理完全部异常时给出"全部异常项已处理完毕"。

### 4. 控件取值回写修复（P0 遗留缺陷）

P0 只回写了 text / textarea / select / date / radio，切换章节后以下类型会丢失编辑：

| 类型 | 修复后行为 |
|---|---|
| 多选（check） | 收集 checked 项文本数组回写 |
| 级联（cascade） | 三级输入合并回写数组 |
| 有/无 + 附件（yn） | 分别回写 `y` 与 `file` |
| 可增行（rows） | 收集全部行输入回写 |
| 技术场景开关（switch） | 回写 `是/否`（P1 重构取值逻辑时一度漏掉该分支，导致切「否」不生效，已补回） |
| 定级报告（grade / concl / subsys） | 分别回写 `desc/obj/harm/lvl`、`text`、`desc` |

### 5. 进度口径修正：场景为「否」时明细不再计入

P0 中把云计算切「否」后，其 6 个明细字段仍在分母里，表4 永远到不了 `19/19`。现在 `flat()` 按技术场景开关过滤，切「否」后：

- 表4 由 `12 / 19` 变 `7 / 13`（分母减 6）；
- 全局由 `103` 变 `97`，底部条分母同步，`② 汇总`与 ① 提示行追加「6 项因场景为「否」无需填写」。

### 6. 定级报告矩阵反推

左侧「受侵害客体 / 侵害程度」两个下拉改动时，按 `客体 × 侵害程度 → 等级` 矩阵（`GRADE_ROWS`）自动重算等级并移动涂黑格，三个控件与矩阵不再可能互相矛盾。
