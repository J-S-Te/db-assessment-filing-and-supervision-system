# 三端办理断点闭环

## 开发目标

- 运营者首报、变更或注销在审时申请撤回，监管明确确认或驳回。审核与撤回串行，原材料、过程和回执保留。
- 机构和运营者在业务时限及详情中能跟踪本人报送的当前审核环节。使用和办理方相同的阶段、工作日及数据范围。
- 监管发布按备案分配的监督检查任务。运营者查收、上传自查材料、提交，监管退回或办结，三端依据同一状态查看。
- 运营者可在测评历史查看对当前单位明确归属的终审报告和整改要求。下载只开放批准时的可交付材料。

## 验证批次

- 每项先复现当前断点，再实现前端、接口、业务校验和状态同步。
- 重点回归失效版本、重复和并发操作、关联对象变动、材料不全、文件冒名和收件范围。
- 统一运行隔离 PostgreSQL 上的 Go 全包竞态、静态检查、构建及前端测试。独立本地预览复跑已有 HTTP 流程与新增三端浏览器操作。
- 登录和 HTTPS 沿用暂缓范围。

## 办理口径

| 业务 | 可用入口和范围 |
| --- | --- |
| 在审撤回 | 运营者从首报、变更或注销详情提出撤回。待监管确认时原审核暂停，监管可同意或驳回。驳回后原审核阶段和原截止日期恢复。监管确认后释放备案号或申请占用，原归属、原材料、过程和回执仍可查。 |
| 报送方审核时限 | 机构、运营者的「业务时限」及单据详情显示本范围的审核环节、办理方和截止日期。申请方关注的在审单据不加入待办计数。日期仍使用现有配置和业务日历，办结后退出时限。 |
| 监督检查自查 | 监管按有效备案建草稿，可由未办结的真实超期线索进入。上传自查表和整改汇总表两份模板后发布至原备案单位。运营者提交两类正式材料，监管退回时指定需替换的材料，补正后重新提交。相同年度备案任务及同一线索通过唯一约束防重复。 |
| 归档测评交付 | 运营者从历史测评的「报告与整改要求」查看该期允许交付的终审正文、报告随附整改规划及已通过的整改要求。服务检查当前本单位备案与报告原归属，禁止将归并前的原件自动开放给新单位。监管保留追溯原件的入口。 |

监督检查候审及运营者待自查进入相应工作台。临期提醒与当前审核状态同源，按进入当前阶段的版本去重。待办或证据归属仍未办结时，单位合并提示先处理该业务。

## 发现及回归

- 审核与在审撤回可能同时发生。服务对同一单据加锁，先写入的有效操作生效，后续操作根据版本和状态拒绝。撤回或通知落库失败时整笔回滚。
- 曾出现已被替换、未随任务下发或未随某轮自查提交的文件可通过旧地址下载。现在运营者模板取下发版本，监管仅能下载列入正式提交历史的结果材料。两种旧地址已在真库和 HTTP 回归验证，符合权限的历史证据继续可查。
- 自查提醒的去重依据采用办理阶段版本。上传材料可提升任务版本，同一阶段同一截止日的提醒保持一条。
- 废弃首报留档和备案号再使用分别处理，从当前备案计数和活动系统退出。重复单位合并时忽略已撤回历史，有尚未办结的自查则阻挡归并。
